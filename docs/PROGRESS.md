- [x] M2 Packet ring buffer (own RTP parser, 0 allocs), NACK generator towards publishers, NACK responder
  (munged SN -> original SN, per-SN throttle, 3 tries), PLI/FIR relay throttled per layer, SR per DownTrack
  from publisher SR, RR to publishers, resume within `resume_window` (server + Go client), hidden recorder
  participants, e2e tests: NACK, PLI throttle, resume, duplicate identity, permissions
- [x] M3 Simulcast: VP8 + H.264 layer switching on keyframes (SN/TS/VP8 picture-id/TL0PICIDX/KEYIDX rewrite,
  7->15 bit picture id, temporal-layer drop with continuous picture ids), keyframe wait with PLI, subscriber
  preferences (`track_setting` quality/size/fps/disabled/priority), Go client simulcast publish (stamps MID/RID),
  e2e switching test (HIGH->LOW->HIGH->MEDIUM, continuous SN/TS/picture id), H.264 IDR switch unit test
- [x] M4 TWCC send-side estimator (`pkg/rtc/bwe`: trendline overuse detector + AIMD + loss bound + ack-rate cap),
  transport-wide sequence numbers stamped by DownTracks, per-subscriber allocator (500 ms tick, priorities,
  3 s upgrade hold for bandwidth upgrades, immediate downgrade, pause + `StreamStateUpdate`), dynacast
  (`SubscribedQualityUpdate`, 10 s grace), e2e: downgrade under a 600 kbit/s policed link and PAUSED at

- [x] M5 Active speaker detection (EMA + 2-interval activation + dominance margin, `speakers_changed`),
  connection quality (`connection_quality` every 5 s, changed entries), mute, single UDP mux port with

- [x] M6 Zero-allocation benchmarks (`pkg/rtc/bench_test.go`: SRTP DownTrack write, fan-out 1/10/100/1000) and
  `TestForwardingDoesNotAllocate`; all 0 allocs/op; `BenchmarkDownTrackWriteRTP` 2.06 us = 486k pkts/s/core with
  SRTP (target 100k). pprof: ~85% of forwarding CPU is SRTP crypto. Details in `docs/perf/WP1.md`

Also done after M6: data packets (`_reliable`/`_lossy` forwarding with destination filtering, Go client
`PublishData`/`OnDataPacket`, e2e), `client.RemoteTrack.OnSenderReport` (WP4 request, satisfies
`recorder.SRSource`, e2e), JoinResponse always first, no congestion control for recorder participants.
AES-GCM SRTP measured at 2.18M pkts/s/core (Pion already negotiates GCM first).

Known issues / next steps (WP1):
- **Firefox**: WP2's browser e2e (CI job `e2e`) passes all Chromium tests but 3 Firefox tests time out waiting
  for remote video (run 41898159870). Not debugged (no Firefox in the session environment). Start by comparing
  the Firefox publisher offer/answer (simulcast RIDs, VP8/H.264 fmtp, header extension ids) and checking whether
  the server receives Firefox RTP (`/stats` published layers) and whether Firefox gets keyframes after PLI.
- RTX from browsers: Pion's RTPReceiver unwraps RTX into `TrackRemote.Read` (verified in Pion source, not by a
  browser test); towards subscribers retransmissions use the primary SSRC (ADR-0006).
- Subscriber transceivers are not reused after unsubscribe (SDP grows in long sessions).
- `SyncState` is answered with a participant update only; ICE restart on resume not exercised server-side.
- Room broadcasts that happen between a participant's admission and its JoinResponse are dropped for that
  participant (JoinResponse already carries the state; a narrow race window remains).
- No padding probes (`congestion_control.probe` ignored).
- Drain sends `leave` with DISCONNECT rather than RESUME/RECONNECT migration; fuzzing only runs the seeds.
- Parallel fan-out shards above `fanout_inline_max` not implemented (inline fan-out only).
